## 1. Q2 vs Q3：模型体积换并发

| | Q3 LynnStyle（16.1 GiB） | Q2 LynnStyle（12.6 GiB） |
|---|---|---|
| 官方三联 GPQA/MMLU/LCB | 173 / **449** / 92 | 177 / **433** / 90 |
| 262K 池下最高并发 | **2 路都不起** | **7 路** |
| 单发 decode | 84-86 | 83.4 |

Q2 省下的 3.8GB 全部转化成并发工作区：Q3 在 262K 池连 mc2 都 finalizing 失败，Q2 一路爬到 mc7。代价集中在 MMLU 知识广度（−16 题）与 MTP 接受率（47.7% vs 67-74%，Q4 头在 Q2 分布上变弱）。

## 2. 并发爬梯（262K 池 + 视觉 + MTP d3）

mc1-mc7 全通（聚合 83.4 单发 → **262.7** @mc7），mc8 ❌。三轮复测：mc7 聚合 285.6 / 316.3 / 284.3（±5%，全表最稳）。

## 3. 48 格全矩阵：mc2-7 × MTP d2-9（含接受率）

- **聚合行最优**：mc2=d2(137.9)、mc3=d4(201.5)、mc4=d3(215.3)、mc5=d2(247.8)、mc6=d4(272.9)、**mc7=d3(316.3 历史峰值)**
- **接受率随草稿长度单调跌**：d2 63-80% → d3 60-64% → d5 45-53% → d9 28-37%
- **接受率跌破 ~50% 的格子聚合必掉**——d5 以上对 Q2 是负资产
- 行最优虽跨会话漂移（±10-31% 会话间方差），但 **d2-d4 高地三轮稳固**；d3 在 Q2 上无特殊甜点地位（那是 Q3 的结论）
- 并发时单路峰值：mc2 × d7 = **95 tok/s**（超真单发 83.4，收尾加速效应）；mc6 × d4 = 76

## 4. KV 格式对决（rk4v4 vs rk8v4 vs fp8 vs bf16）

| 格式 | 实测单价 | mc6 可用池 | 单发 decode | 接受率 |
|---|---:|---:|---:|---:|
| **rk4v4（FP4 系）** | 19 KB/tok | **288K** | **84-86** | 67-74% |
| fp8 | 32.6 KB/tok | ~131-148K | 80.7 | 67.6% |
| rk8v4 | 28.6 KB/tok | ~160-176K | 63.6 | 44.4% ⚠ |
| bf16（默认） | 52.7 KB/tok | ~64-96K | ~81 | — |

**rk4v4 全面胜出**：decode 是带宽瓶颈，KV 读得越少越快。rk8v4 的接受率腰斩（疑草稿头读 4-bit V 受损）。

## 5. 池天花板探针（mc6 × d3）

262,144 ✅ → 266,240 ✅ → 278,528 ✅ → **294,912（288K）✅** → 303,104 ❌ / 311,296 ❌。
**天花板 288K**，边界在 288-296K 之间。教训：引擎的「free 0 B」偏保守，真实边界必须探针实测。终版取 max-context 262,144（原生窗口）+ 池 294,912（+32K 排队余量）。

## 6. 启动故障档案（`finalizing target` 秒炸的根因链）

1. 默认 KV 是 **bf16（52.7KB/token）**——262K 池要 13.3GB，必炸
2. `--kv-capacity auto` 在大 max-context 下分配失败——**显式指定**
3. 官方 96GB 卡配方（池 819,200）照抄必炸
4. 每加一路并发 ≈ +0.5-1GB 工作区；**长草稿在高并发下也吃工作区**（mc7 × d8/d9 起不来）
5. mc8 带视觉 = d2-d9 全灭；mc9 是引擎硬限制（1..8）

## 7. 视觉

`--vision` 代价 ~0.3-0.5GB（权重 16.1→16.4 档位的包内组件）。实测红底/白框/双色文字 OCR 全对，decode 70.1 tok/s。262K 池下装不下视觉（Q3），Q2 可以。

**补充实锤（10-16）**：Coder390 包内 chat template 的缺省 effort = **xhigh**（NInfer-all 官方协议原文 "thinking on (template default xhigh)" ×3 处）——即不设任何参数时请求本就跑在 xhigh 上；`--default-reasoning-effort xhigh` 是显式双保险。引擎无"无视请求 effort"的强制 flag；模板硬编码锁（--chat-template 注入）为备选未启用。

### 窗口边界行为实测（10-16，来自外部 Harness 报障排查）

| 场景 | 引擎行为 |
|---|---|
| 提示 ≤ max-context，但 提示 + 请求 max_tokens 超窗 | ✅ 自动裁剪 max_tokens 到剩余空间（实测 254,762 prompt + 8192 请求被接受） |
| 提示本身 > max-context（262,144） | ❌ HTTP 400 `context_length_exceeded`（**无自动裁剪历史**） |
| 请求不传 max_tokens | 引擎默认 = "每路同时入场提审的最大预算 + 单路剩余上下文"（池级大数） |

推论：外部 Harness 的「输出截断」= Harness 自身 max_tokens 帽（在 Harness 设置里调大）；「400 超窗」= Harness 无限累积历史超过 262K 原生窗——引擎不裁历史，**历史管理必须在 Harness 侧做**（或将来测 --rope-yarn 扩窗，质量未验证）。
